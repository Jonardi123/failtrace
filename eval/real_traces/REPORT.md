# Real agent trace audit — 2026-09-05

**Verdict: useful for narrow advisory triage, not validated as a general automatic quality gate.**
The merged PR #3 baseline found two real command-error streaks, but gave no
warning for a much longer stalled repair. A focused FT008 change now detects one
unchanged-diagnostic streak in that run. This is an exploratory audit and a
regression fix on the same sample, not a held-out accuracy result.

Total: **366 calls, 354 recorded results, 58 nonzero returns**. Five nonzero returns

They were preserved, not automatically treated as either bad behavior or

## Conversion and provenance

[manifest.json](manifest.json) pins every source URL, SHA-256, ETag, model and
instance ID, plus the normalized file's SHA-256. Artifact URLs are not versioned;
the collector rejects changed bytes instead of silently accepting a different
run. Original downloads are cached locally and never executed or republished as
part of the repository. [collect.py](collect.py) has no AI or agent dependency.

Each executed bash block becomes one `run_command` call; compound shell commands
remain a single call. Matching observed return codes determine `ok` exactly.
Arguments contain the recorded command; working directories are not invented.
Recorded output is retained for review, including output from successful calls.
Optional provenance, original message indices, and unknown-result notes are
extra metadata already allowed by `agenttrace.v1`. Model thoughts and task
prompts are not included in normalized traces. Neither public schema changes.

The exporter ends each run with a submission diff rather than a return code.
All 12 final calls are retained with no fabricated result. Two source-file reads
(R09 message 5, R11 message 7) have publisher-truncated output, explicitly marked.
The gate is given a limit of 10,000 findings, and all 12 runs were checked; the
default output cap did not censor this audit.

R01 contained **34 failed reproduction checks and one malformed edit command**.
The baseline found none of that run's stalled-repair behavior. The new rule
catches the repeated identical-diagnostic segment; it does not claim to detect
every ineffective edit or all 34 failures. Ordinary reproduce/edit/retest cycles
are necessary. Here the evidence for a warning is the same diagnostic persisting
through repeated attempts, not merely the presence of failed tests.

There were **no clear false positives among the two original findings**. The new
warning was also reviewed in context. No other warnings or errors appeared after
the change. The baseline and replay are preserved in [baseline.json](baseline.json)
and [after.json](after.json).

## What remains missed or unscorable

These limitations were inspected rather than converted into speculative rules:

- **Failures hidden by a pipeline:** R04 message 7 reports a missing file from
  `nl`, while `head` leaves the shell result at zero. The agent then corrects the
  path. This is a real inner-command failure hidden from status-only checking,
  but not a demonstrated bad recovery. The trace has no per-process status.
- **Output without an assertion:** R06 prints an unchanged symbolic result
  across several zero-exit runs before a later output becomes numeric. R01 also
  reaches zero exit while its printed reproduction is still wrong, then changes
  it later. Expected task results require domain context; parsing arbitrary
  stdout as a failure would invent a verifier the trace does not supply.
- **Unverified test execution:** R12 runs a test module directly after discovering
  pytest is missing. It exits zero with warnings but no test-completion summary.
  The gate cannot establish how many tests ran.
- **Incomplete observations:** the 12 final submission outcomes and two truncated
  reads remain ambiguous/insufficient data. A submitted patch is not proof of a
  correct patch.
- **Untested rule coverage:** this sample provides no positive validation of
  FT001–FT007. All tools are shell calls, so path-specific rules receive no
  structured file paths. There are no observed parallel tools in this corpus.
  Regression boundary tests for parallel cases are synthetic controls, not real
  coverage claims.

These cases are documented as ambiguity or coverage limits in the review ledger.
M1 is the one clear recovery-regression miss identified under this audit's
scope; it has a regression test and fix. Single errors followed by defensible
recovery are not counted as misses. This audit does not measure task success,
all possible semantic mistakes, or general recall.

The requested false-positive figure is **0% of the observed alerts**, with a
very small denominator. This is not the population false-positive rate
`FP / (FP + TN)`: a representative set of negative decision opportunities was
not exhaustively labeled. Zero false alarms out of two original alerts does not
establish reliable precision. The third alert was added using this same sample,
so its success is regression confirmation, not independent validation.

Both before and after, the default error-level gate would accept every sampled
run. The useful signal here is advisory and requires reviewing warnings.

## Exact changes and new tests

- `gate_rules.py`: extend existing **FT008**, still warning severity. Track an
  exact shell-tool call and its complete error object across intervening
  activity; emit one warning on the third matching nonempty diagnostic. Reset
  on a success of that same call, a changed error or a missing diagnostic. Keep
  different arguments/environments separate. Late parallel results cannot
  resolve or extend a recovery streak that their call predates. Preserve the
  original consecutive-error condition and avoid duplicate FT008 reports.
- `tests/test_real_trace_regressions.py`: **10 cases**. One reduced regression
  from R01; controls for success/changed/empty diagnostic resets, distinct
  environments, two-attempt silence, empty grep output, one alert per streak,
  late parallel success, and concurrent calls that are not recovery attempts.
  The R01 regression fails against the merged PR #3 baseline.
- `tests/test_real_trace_collection.py`: **7 cases** protecting source conversion:
  nonzero empty output versus zero-with-error-text, text-block messages, unknown
  final results, truncation, malformed statuses, and source checksum rejection.
- `eval/real_traces/`: the pinned manifest, audit-only collector and replay
  checker, original and updated gate reports, per-run/per-finding reviews, and
  this report. No production adapter framework or unrelated feature added.
- `README.md`, `docs/GATE.md`, `CHANGELOG.md`: document the behavior and its limits.

`failtrace.v1`, `agenttrace.v1`, their normalizers, the generated datasets, and
the existing evaluator/scoring protocol are unchanged.

## Reproduce

From a checkout containing this change:

```bash
python -m pip install -e ".[test]"
python eval/real_traces/collect.py --work-dir /tmp/failtrace-real-audit
failtrace-gate /tmp/failtrace-real-audit/agenttrace.jsonl --max-findings 10000 --format json --fail-on never -o /tmp/failtrace-real-audit/gate.json
python eval/real_traces/check_audit.py /tmp/failtrace-real-audit/agenttrace.jsonl
python -m pytest -q
```

Use `--offline` on the collector to require previously downloaded sources. It
checks every source hash again. The replay checker verifies the normalized hash,
run IDs/order, complete nonzero-result inventory, and every finding against the
persisted audit. `--fail-on never` above is for report capture only, not a
recommendation to weaken a production gate.

The baseline commit is `b3a424575366abed018d19c7f1541de5c2eb7709`; lint the same
normalized file in a worktree at that commit to reproduce `baseline.json`.

## Verification and conclusion

Local verification: **67 tests passed** on Python 3.12 with pytest 8.4.2. The
new real-case regression fails on the baseline. Replaying all 12 source-hash-
verified runs matches the three reviewed warnings exactly. Generated 200 rows
validated; SFT packing and the reference harness/gate smoke checks pass.
The reference harness results (gold 11/11, exact retry 0/11) are synthetic sanity
checks, not measurements on these 12 real runs.

CI uses the repository's existing Python 3.10, 3.11, 3.12 and 3.13 matrix.
Its final status is linked from the pull request containing this report.

**Usefulness today:** a small tool that can point a reviewer toward certain
obvious failed-recovery patterns. It is not yet evidence-backed enough to claim
that a green gate means good agent behavior, a successful repair, or broad
failure-recovery coverage. The next validation should use previously unseen,
unpaired real runs and at least one framework with structured file tools.
